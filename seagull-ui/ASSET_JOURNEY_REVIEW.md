# Asset 使用复盘工作流

用于记录一次 Asset 创作的停顿、手动补救、可用测量数据和最终采用情况。它是人工确认的复盘工作流，不是自动行为埋点，也不是文章质量评分器。

## 使用

1. 在任意 Asset 页面点击 **Review Journey**。如有未保存编辑，先保存，或确认离开并保留浏览器恢复草稿。
2. Chat 自动选择 **Review Asset Journey**，填入当前 Asset 的已保存状态快照；点击发送开始复盘。也可在 Chat 的 Decide 工作流中直接选择，手动提供记录。
3. Agent 询问尚未提供的反馈：在哪一步停住及原因、手动补救及结果、是否有耗时／重试／用量记录、成品是否采用及原因。可以回答无阻塞、仍在进行、暂未决定或不知道。
4. 核对报告及末尾的结构化 JSON 摘要后点击 **Save as Review Note**。缺少有效摘要、Asset ID 不匹配或指标格式错误时会拒绝保存，并提示让 Agent 修正；访谈问题不能当作最终报告保存。未明确保存时，不会创建复盘笔记，也不会修改 Asset。

保存的笔记带有 `workflow:review-asset-journey`、`asset-journey-review` 标签；从 Asset 发起时另带 `asset:<id>`，方便检索同一 Asset 的多次复盘。复盘日期和 Asset ID 也应保留在正文中。

## 数据与边界

| 记录 | 首版来源与限制 |
| --- | --- |
| 当前页面、Asset 状态、编辑是否未保存 | 页面快照；当前页面不代表用户停住的位置 |
| Evidence／Claim 数量、导出阻塞、质量审计 | 已加载的当前状态；不是完整操作历史，缺失数据标为未知 |
| 已保存优化轮数 | Asset 元数据；不等于重试次数 |
| 图片任务、模型、处理次数、时间戳 | 已加载的视觉任务记录，最多附带 30 条，并注明总条数 |
| 图片任务经过时间 | 创建到完成，包括排队和重试等待；不是纯模型推理耗时 |
| 各阶段等待、全程重试、模型 Token／成本 | 尚无统一采集；用户可补充脱敏测量，未提供就标为未知 |
| 停顿原因、手动补救、实际采用 | 用户反馈；导出或发布状态不能代替实际采用确认 |

报告区分 `system_record`（系统记录）、`user_report`（用户反馈）、`user_estimate`（用户估计）、`unknown`（未知）；原因推测标为 `hypothesis`。估计不与实测混算。

快照不附带正文、图片提示词、下载 URL 或任意元数据；只附带状态、任务指标及已有编辑／发布反馈（单字段最多 4,000 字符）。Agent 不应索取凭据或完整私人日志，不联网搜索补齐指标。访谈与报告仍会进入所选模型的会话上下文。

## 后续分析

在 **Settings → Dashboard → Asset Diagnostics** 查看全局统计（`/stats?tab=assets`）。Asset Library 的 **Function Statistics** 也直达该标签，旧 `/assets/journey-stats` 自动跳转。Dashboard 分为 Overview（总览）、Knowledge Usage（使用排行）和 Asset Diagnostics（全局功能卡点）三个标签，刷新页面会保留所选标签。主统计通过 Gateway 调用只读 `/assets/analytics`，聚合当前登录用户的全部 Asset，不要求先写复盘，也不受列表分页限制。

- 功能矩阵：Intent、Evidence、Claims、草稿、内容 Blocks、整篇优化、质量、Outline、生图、导出、微信投递、知识沉淀，共 12 个功能区。
- 每区展示已完成、前置条件阻塞、待审阅、进行中、未开始与未知；仅有留存失败记录的功能显示失败统计。可选功能未使用不等于失败。
- 卡点分布与明细：汇总已保存状态中的原因，按功能查看受影响 Asset 和具体 Block，并跳转对应功能页。明细分页不截断全局计数，支持类型、状态筛选与刷新。
- 图片指标：全部视觉任务、失败、处理尝试、重试与创建到完成的平均耗时；保留旧失败候选，但不把已有接受图片的 Asset 判为生图失败。
- 范围：含归档 Asset，只覆盖当前用户；缺少工作区的旧版／自动生成 Asset 保留未知。读取不修改工作区或更新 Outline。

主页面是**当前持久化状态的诊断**，不是用户真实停顿历史。各阶段等待、Harness 重试、Token／成本、手动补救和实际采用尚未统一采集，不能从状态推断。展开 **User-reported journey reviews (supplementary)** 才加载用户显式保存的复盘，补充以下分析：

- 概览：有效复盘数、关联 Asset 数、报告停顿／手动补救的复盘数、完整采用率。
- 分布：各步骤的停顿与补救次数、采用状态、原始措辞的停顿原因，以及部分采用／未采用原因。
- 指标：按具体范围、指标、单位和来源分别展示样本数与平均值；实测、用户反馈和估计不混算，未知值不计为零，图片耗时／处理次数不冒充全程等待／重试。
- 记录：查看原始 Note 与关联 Asset，按关键词和保存日期筛选，支持“每个 Asset 最新有效复盘”和“所有复盘”两种口径。

统计仅覆盖带 `asset-journey-review` 标签且结构化摘要通过校验的已保存笔记，不代表全部 Asset 或全部用户操作。旧版自然语言报告、格式错误或身份不匹配的记录仍可查看，但不猜测或自动转换成指标；可重新运行复盘生成有效摘要。

默认在筛选范围内取每个关联 Asset 最新的有效复盘；未关联 Asset 的复盘独立计数。“所有复盘”模式会重复计入同一 Asset 的多次复盘。每个复盘在同一步骤最多计一次停顿／补救。

完整采用率 = `yes / (yes + partial + no)`。进行中、未决定和未知不进入分母，无已决定样本时显示未知而非 0%。用户估计、原因推测仍需人工核对，结构校验不能验证事实。

日期按笔记创建时间（UTC）筛选，不使用模型生成的日期。页面通过现有 Notes API 分页加载，每次最多加载 2,000 条，达到上限或发现分页缺口时明确提示样本不完整；刷新后重新加载。

结构化摘要使用单个 `json` 代码块，包含 `kind: asset_journey_review`、`schema_version: 1`、`asset_id`、`stops`、`manual_recovery`、`adoption`、`metrics`。保存校验和页面解析共用同一份定义。未知使用 `unknown` 与 `null`；只有明确确认无停顿／补救时才使用 `none`。

当真实复盘显示测量缺口影响决策时，再增加 PKG 持久化的 Journey Run／Event、Gateway 或 Harness 的用量关联与阶段耗时采集。不要把当前快照包装成完整会话遥测。
