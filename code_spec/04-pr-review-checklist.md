# PR 审查清单

> 适用场景：后端服务、AI 应用、RAG、Agent、后台任务的 Pull Request 审查  
> 使用方式：Reviewer 按 P0 / P1 / P2 分级给出意见，P0 必须修复后才能合并

---

## 1. 审查原则

Code Review 的目标不是找茬，而是确认：

- 代码正确实现需求。
- 设计与项目架构一致。
- 风险被识别和控制。
- 线上问题可排查。
- 未来维护者能理解和修改。

Review 意见应包含：

- 问题等级：P0 / P1 / P2。
- 具体位置。
- 为什么这是问题。
- 推荐修改方向。

---

## 2. P0 阻断项

### 安全

- [ ] 是否存在硬编码密钥、Token、密码、生产地址？
- [ ] 是否把敏感信息写入日志、错误响应或前端返回？
- [ ] 是否存在越权访问风险？
- [ ] 文件上传是否缺少大小、类型、路径限制？
- [ ] CORS、鉴权、权限策略是否被错误放宽？

### 输入与输出

- [ ] 用户输入是否未经校验直接进入业务逻辑？
- [ ] 是否存在用户输入拼接 SQL？
- [ ] API 响应是否泄露内部字段？
- [ ] 错误响应是否暴露堆栈或内部实现？

### 事务与数据一致性

- [ ] 事务边界是否不清晰？
- [ ] 重要写操作是否缺少幂等设计？
- [ ] 是否可能重复扣款、重复发货、重复发消息？
- [ ] 是否在 repository 中随意 commit？
- [ ] 外部 HTTP 调用是否放在数据库事务中长期阻塞？

### 外部调用

- [ ] 外部 HTTP 调用是否缺少 timeout？
- [ ] 重试是否可能放大故障或造成副作用？
- [ ] 第三方异常是否未转换就透传？
- [ ] 非幂等操作是否盲目重试？

### 数据库迁移

- [ ] 是否有 schema 变更但没有 migration？
- [ ] migration 是否包含危险操作且无说明？
- [ ] 大表变更是否可能锁表？
- [ ] 是否直接删除字段或修改字段类型而无兼容策略？

### AI / LLM

- [ ] LLM 调用是否缺少 timeout？
- [ ] 模型输出是否未经 schema 校验就进入业务逻辑？
- [ ] 高风险工具调用是否完全由模型决定？
- [ ] 工具调用是否缺少权限检查？
- [ ] RAG 内容是否可能覆盖 system prompt？
- [ ] 日志是否记录完整敏感 prompt、用户隐私或模型凭证？
- [ ] Prompt 或模型变更是否没有版本和评测？

---

## 3. P1 重要项

### 架构与分层

- [ ] 路由函数是否过重？
- [ ] Service 是否依赖 FastAPI HTTP 细节？
- [ ] 数据访问逻辑和业务逻辑是否混在一起？
- [ ] 是否引入了不必要的复杂抽象？
- [ ] 新代码是否符合项目现有风格？

### 错误处理

- [ ] 是否存在 `except Exception: pass` 或吞异常？
- [ ] 异常是否缺少日志和上下文？
- [ ] 业务异常是否有稳定错误码？
- [ ] Pydantic 校验错误是否统一格式化？
- [ ] 数据库约束错误是否转换为业务异常？

### 日志与观测

- [ ] 请求日志是否包含 request_id？
- [ ] 错误日志是否能定位问题？
- [ ] 是否缺少关键业务资源 ID？
- [ ] 是否缺少慢请求或外部调用耗时记录？
- [ ] 是否影响已有监控指标？

### 性能

- [ ] 是否可能产生 N+1 查询？
- [ ] 列表接口是否缺少分页上限？
- [ ] 高频查询是否缺少索引考虑？
- [ ] 是否在 async 函数中调用阻塞 IO？
- [ ] 批量并发是否缺少上限？

### 测试

- [ ] 核心业务逻辑是否缺少单元测试？
- [ ] API 关键路径是否缺少集成测试？
- [ ] Bug 修复是否缺少回归测试？
- [ ] 外部服务是否没有 mock？
- [ ] 测试数据是否难以维护或相互污染？

### AI 工程

- [ ] 是否直接在业务代码中调用供应商 SDK？
- [ ] Provider 差异是否没有 adapter 吸收？
- [ ] Prompt 是否散落在代码字符串中？
- [ ] 结构化输出失败是否缺少 retry、repair 或降级？
- [ ] 工具参数是否缺少 schema？
- [ ] RAG 检索结果是否缺少来源记录？
- [ ] 多轮对话是否无限追加历史消息？
- [ ] 流式输出是否没有 completed / cancelled / timeout / error 状态？
- [ ] 是否缺少 token、model、prompt version、latency 记录？
- [ ] 是否缺少 eval 或 smoke eval？

---

## 4. P2 建议项

### 可维护性

- [ ] 命名是否可以更清晰？
- [ ] 函数是否承担了多个职责？
- [ ] 是否存在重复代码？
- [ ] 注释是否解释了"为什么"，而不是重复"做了什么"？
- [ ] 是否需要补充文档或示例？

### 扩展性

- [ ] 是否有明显未来扩展点但当前实现封死？
- [ ] 是否需要抽象成 client、service、repository？
- [ ] 是否需要引入缓存、队列、限流或 tracing？
- [ ] 是否需要配置化而不是硬编码？

### AI 质量

- [ ] Prompt 是否可以更明确输出格式和约束？
- [ ] Eval 样例是否覆盖边界输入？
- [ ] 是否需要人工标注流程？
- [ ] 是否需要缓存来降低成本？
- [ ] 是否需要多模型路由或降级模型？
- [ ] 是否需要输出安全过滤或 guardrails？

---

## 5. PR 描述检查

PR 描述应包含：

- [ ] 变更目的。
- [ ] 核心实现方式。
- [ ] 测试方式。
- [ ] 风险点。
- [ ] 回滚方案，若涉及生产风险。
- [ ] 配置变更，若有。
- [ ] 数据库 migration，若有。
- [ ] Prompt / model / eval 变更，若有。

推荐格式：

```md
## Summary

- ...

## Test Plan

- ...

## Risk

- ...

## Rollback

- ...
```

---

## 6. AI 变更专项检查

当 PR 涉及 Prompt、模型、RAG、Agent、工具调用时，额外检查：

- [ ] Prompt 是否有版本号？
- [ ] Prompt 修改是否跑过 eval？
- [ ] 模型切换是否有质量和成本对比？
- [ ] 工具 schema 是否更新？
- [ ] 工具权限是否仍然正确？
- [ ] RAG index 是否变更？
- [ ] 上下文窗口策略是否改变？
- [ ] 流式输出协议是否兼容前端？
- [ ] 是否影响 token 成本？
- [ ] 是否影响用户隐私或数据合规？

---

## 7. 数据库变更专项检查

当 PR 涉及数据库 schema 或数据迁移时，额外检查：

- [ ] migration 是否可读并经过人工 review？
- [ ] 是否兼容旧代码和旧数据？
- [ ] 是否需要分阶段发布？
- [ ] 是否有回填脚本？
- [ ] 回填是否可中断、可续跑？
- [ ] 是否会长时间锁表？
- [ ] 是否有回滚或补偿方案？

---

## 8. 后台任务专项检查

当 PR 涉及后台任务、队列、定时任务时，额外检查：

- [ ] 任务是否幂等？
- [ ] 是否有重试上限？
- [ ] 是否有死信或失败记录？
- [ ] 是否有任务超时？
- [ ] 是否记录关键日志？
- [ ] 是否支持中断和续跑？
- [ ] 是否会重复执行产生副作用？

---

## 9. 常见反例

以下问题通常应要求修改：

- 在路由函数中写大量业务逻辑。
- 直接返回 ORM 对象且不控制字段。
- `except Exception: pass`。
- 在 `async def` 中调用 `requests`。
- 外部 HTTP 请求不设置 timeout。
- 用户输入拼接 SQL。
- 日志打印 Token、密码、Cookie。
- 列表接口无限制返回所有数据。
- Prompt 修改不评测直接上线。
- 模型输出自然语言直接驱动关键业务动作。
- Agent 无最大步骤数和预算限制。
- 流式输出失败后仍标记为成功。

---

## 10. Review 结论模板

无阻断问题：

```text
LGTM。主要路径清晰，测试覆盖了关键场景。建议后续关注 ...
```

有 P1 / P2 建议：

```text
整体方向没问题，有几个建议项：
- P1: ...
- P2: ...
```

有 P0 阻断：

```text
当前不建议合并，存在 P0 阻断项：
- P0: ...

修复后我再复查。
```
