逐轮实施与验证记录：[V2 优化实施记录](v2-progress.md)。

## 产品目标

让用户从一个新的技术话题，或一项「调研并决定」的待办出发，获得**与自己的长期目标、项目和知识水平相关**、有可核验外部证据的研究结论，并在本人确认后沉淀为笔记、知识产出与后续行动。

主路径：**话题 / 待办 → 本次使用的个人上下文 → 研究计划 → 内外部检索 → 可核验发现 → 审阅与产出 → 待办后续行动**。

粘贴网址、上传文件是补充证据入口，而不是首次研究的必经步骤。研究结论、个人长期记忆和事实证据必须分开：记忆决定「为什么研究、关注什么」，不能充当「外部事实已被证明」的依据。

## 现状与设计约束

- `seagull-ui/src/pages/ChatPage.tsx` 已支持 `/deep-research`；`DiscoverPage.tsx` 已有网页搜索，但目前并非同一条从话题到产出的连续路径。
- `personal_knowledge_graph/src/pkg/services/cross_cutting/user_profiler.py` 能生成活动画像；`bff/src/index.js` 为聊天召回已确认的 Agent Memory。先盘点两者的生命周期与用户控制方式，再决定如何为单次研究组合上下文，避免同步出第二套长期记忆。
- `personal_knowledge_graph/src/pkg/services/application/asset_workspace.py` 已有 Intent、Evidence、Claim 和质量门禁；优先复用 Asset 工作区，避免把「研究」另建成与 Asset 平行的持久化概念。确有无法表达的场景再提交设计决策。
- `CalendarReminder` 已能关联 Note，尚无完整的待办 → 研究产出 → 决策关系。该关系由 PKG 持久化；浏览器和 Harness 仍经 Gateway 访问 PKG。
- Agent 搜索、草拟和提出建议不等于用户同意长期保存、修改待办或发布。V2 维持现有的显式确认边界。

## 排期顺序

### P0：话题研究闭环（先验证核心价值）

**V2-01 研究入口与可恢复状态**

- 用户在首页或 Chat 输入一个话题/问题，即可启动研究；优先复用 Chat 的深度研究和 Asset 工作区。支持选择「快速了解」或「支持决策」，不要求先导入 Source、配置 Wiki 或填写完整 Asset 表单。
- 在 PKG 中记录研究问题、状态、所选范围、关联会话和资产 ID；刷新、任务失败或中断后能继续，不重复创建资产。UI 呈现「规划中／检索中／待核验／待审阅／已确认／失败」及重试入口。
- 验收：新用户从一句话开始能得到一份可继续编辑的研究草稿；中断重试不丢失提问、证据或确认状态。新增跨 Chat、Gateway、PKG 的集成测试及 UI 关键流程测试。

**V2-02 本次研究的个人上下文**

- PKG 提供按当前话题挑选的用户画像信号、相关 Notes/已确认结论、正在进行的项目或待办；Gateway 合并已确认 Agent Memory，并返回结构化、限量的「本次参考背景」。保留各条的来源、明确/推断属性、更新时间和关联理由。检索不够准确时允许仅靠用户提供的目标启动。
- 发起研究前展示可移除、可编辑的背景项和「不使用个人记忆」开关；用所选背景生成研究计划和搜索方向。记录本次使用的背景快照以便复盘，但不因此修改长期记忆。不同用户的数据必须严格隔离。
- 验收：用户可解释为什么助手优先比较某些方案；关闭记忆后研究仍可运行；改变/撤销背景只影响本次研究；过期或推测的偏好不冒充已确认事实。

**V2-03 计划驱动的内外部研究**

- 先生成可调整的研究问题、比较维度与检索计划；复用 PKG 检索、网页搜索和现有 Deep Research 能力，给出知识库已有内容、外部新发现与信息缺口。普通研究尽量减少确认步骤；需要调用高成本服务或对外发送可能敏感的个人上下文时明确提示。
- 外部检索只发送任务所需的去标识化查询，默认不发送用户画像、私人 Notes 或待办原文。仅搜索结果摘要不能标为已阅读原文；检索失败和来源不可访问要清楚显示。
- 验收：给一个库中不存在的话题也能检索外部资料、展示来源和日期、形成可审阅发现；无效/受限网页不会被写成已核实证据。

### P1：将「可信」变成可操作的核验体验

**V2-04 逐条结论的证据核验**

- 在研究结果正文旁直接展示关键结论对应的证据状态：「已找到原文定位／仅有来源但无法定位／与其他证据矛盾／缺证据／用户已核验」。点击后显示原文片段、来源位置、检索时间和该结论为何受支持；能退回、标注冲突或请求补证据。
- 复用 Asset Evidence/Claim 的 `fragment_selector`、支持/矛盾关系和现有门禁，补齐片段缺失、原文已变、引用与文本不符的检测及测试。将「自动检查通过」和「用户已核验」明确分开，不暗示系统保证事实正确。
- 验收：任何关键结论都能追到可打开的原始来源，或被明确标记为无法核验；无证据和未解决的冲突不能显示成「已核验」，导出前必须看到相应风险。

**V2-05 从研究到可审阅产出**

- 用现有 Asset/Note 能力将研究整理成简报或决策备忘录：分开「客观发现」「结合我的背景的判断」「待确认的问题」「建议下一步」，引用已核验的来源。用户决定保存哪些内容；不自动发布或将推断晋升为 Wiki 事实。
- 验收：用户能将一次研究保存为可恢复、可编辑的成果；再次打开仍能看到当时选用的个人背景与证据核验结果。

### P2：待办、笔记和研究成果形成闭环

**V2-06 从待办发起研究，并关联成果**

- 在日历待办增加「研究这个问题」；将待办 ID 传入同一研究入口，而不是复制出第二套流程。PKG 持久化待办与已有 Notes、研究成果的关联；支持查看研究进度、最新结论和待解决问题。
- 研究形成结论后建议创建下一步待办或更新原待办，由用户确认。草稿生成不自动完成待办；删除、取消关联和权限边界需要在 PKG/BFF/UI 同步处理。
- 验收：从待办一键进入研究，返回待办仍能打开原研究与引用的笔记/产出；取消/删除关系不会意外删除研究成果。

**V2-07 经确认的记忆反馈**

- 研究结束时建议记录稳定的个人偏好、项目约束或已作出的决策；用户可接受、修改、拒绝及删除。阶段性猜测与外部事实不直接写入 Agent Memory 或用户画像；确认后的记忆在后续相关研究中可见并可撤回。
- 验收：同一话题后续研究能利用已确认的约束；错误的画像推断或一次性结论不会自动污染长期记忆。

## 验证方法与发布门槛

先做 5–10 次目标用户走查，再确定上线阈值；以下是**目标而非已验证数据**：

- 从输入话题到看见带来源的首份研究草稿的时间、完成率和失败/放弃节点；分别观察空知识库和已有大量知识的用户。
- 盲测同一话题的「无记忆」与「可编辑个人上下文」研究计划：记录用户认为真正有用的差异，以及错误使用、过度迎合个人偏好的次数。
- 抽检关键结论的原文定位成功率、证据与结论是否吻合、矛盾是否显示；只看引用数量不足以衡量可信度。
- 从待办出发的研究完成率、结论被保存/采纳率、后续行动被创建率。事件仅采集流程状态与必要 ID，不把私人查询、记忆内容或原文上报到第三方分析平台。

每阶段先运行服务本地测试，再运行对应跨服务集成与 Seagull UI 关键流程测试。未通过证据追溯和用户确认边界前，不把研究结果宣传为已验证结论。

## 本轮不做

- 不以批量资料导入、知识图谱展示或新增连接器作为 V2 主路径。
- 不开发独立于 Asset 的第二套研究成果/证据存储，除非现有模型验证确实不足。
- 不让模型自行发布、自动完成待办，或把推测性的用户特征当作确定事实。
